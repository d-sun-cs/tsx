# FastTT-LRC：实现说明

代码主体是 `ErasureCodeTsxLrc.h/.cc`。`mode=fasttt` 实现移位 XOR 全局校验和联合恢复。`mode=fasttt-redis` 将移位尾部存入 Redis，输出等长分片。`mode=scaffold` 保留 ISA-L 全局码作为对照。

## 1. 布局：原数据只切一次

以32KiB输入、8个数据片、每片4KiB为例。map的key是片号，片内偏移才是字节位置。

| 片号 | 本次输入范围 | 原tsx：8+3 | 新tsx_lrc：8+2+2 |
| --- | --- | --- | --- |
| 0 | [0,4) KiB | D0 | D0 |
| 1 | [4,8) KiB | D1 | D1 |
| 2 | [8,12) KiB | D2 | D2 |
| 3 | [12,16) KiB | D3 | D3 |
| 4 | [16,20) KiB | D4 | D4 |
| 5 | [20,24) KiB | D5 | D5 |
| 6 | [24,28) KiB | D6 | D6 |
| 7 | [28,32) KiB | D7 | D7 |
| 8 | 计算得到 | G+ | G+，向前移位 XOR |
| 9 | 计算得到 | P0 | G−，反序移位 XOR |
| 10 | 计算得到 | G− | L0＝D0 XOR D1 XOR D2 XOR D3 |
| 11 | 计算得到 | 无 | L1＝D4 XOR D5 XOR D6 XOR D7 |

数据满足 `Di[t]=in[i*4096+t]`。`m=2` 计全局校验，实际共有4个校验、12片。以32字节为单位，`G+[t]=XOR_j D_j[t-j]`，`G−[t]=XOR_j D_j[t-(7-j)]`，越界为零。此例完整 G± 各4320字节，数据和局部校验各4096字节。输入不足一条带时由基类补零。

| 模式 | 全局片输出 | 完整 G± 的获取方式 |
| --- | --- | --- |
| `fasttt` | 4320B | 片内直接包含全部校验字节 |
| `fasttt-redis` | 4064B 校验前缀＋32B SHA-256 摘要 | 按摘要取回最后32B主片和224B尾部，拼回4320B并校验摘要 |

Redis 模式的摘要从完整 G± 计算。即使两个条带的全局校验前缀相同，尾部有差异时也各有自己的键。局部修复只使用组内四片。联合解码只读取所选全局片的元数据，重建全局片后重新写入相应元数据。

## 2. 接口：Ceph准备缓冲，插件填写数据

我们与官方LRC一样继承 `ErasureCode::encode/decode/decode_concat`，只实现所需的低层计算与选片扩展，不修改OSD或ECUtil调用逻辑。上层按条带调用，插件收到的未必是整个对象。

| 低层参数 | 进入函数时的内容 |
| --- | --- |
| `encode_chunks(want, encoded*)` 的want | 要交回的片号；默认写入为全部12片 |
| encoded | 0～7已有数据，8～11由基类预分配。FastTT写入8、9前扩展全局输出；基类最后按want保留结果 |
| `decode_chunks(want, chunks, decoded*)` 的want | 要求有效的输出片号；前台通常为全部数据0～7，后台重建为本次缺片 |
| chunks | 实际读回的有效片；缺key也可能只是没读，不能用全零片冒充缺片 |
| decoded | 基类引用输入并按首个输入片长分配缺片空间。FastTT按实际目标重新确定片长，恢复结束后移除未填条目 |

公开encode/decode调用的输出map初始为空；进入_chunks前空间已准备好。chunks与decoded是不同map，已读片通常共享底层字节，对齐重建可能产生复制。计算函数返回0／负错误码，实际结果写进bufferlist。

## 3. Layer：我们维护的编码任务表

官方LRC把若干次编码组织为Layer，层的输入可以包含之前生成的校验。其常见高层布局把数据与全局校验一起局部分组；我们仅对数据分组。Layer是插件内部结构，不是Ceph额外传入的参数。

| 本插件的Layer | 输入 → 输出（外层片号） | 子编码器的编号 |
| --- | --- | --- |
| global | 0～7 → 8、9 | 0～9 |
| local0 | 0、1、2、3 → 10 | 0、1、2、3 → 4 |
| local1 | 4、5、6、7 → 11 | 0、1、2、3 → 4 |

`layers_init()`创建任务，`layer.chunks=data+coding`规定重编号顺序。各层引用同一批数据缓冲。ISA-L 子编码器使用层内编号，计算结果映回外层。FastTT全局编码和联合恢复直接用外层编号，便于同时引用组内校验和全局校验。

## 4. 用D2恢复串起选片、计算与输出

```text
目标want={2}，其余片可读
  → minimum_to_decode选择{0,1,3,10}
  → Ceph只读取这四片，形成chunks
  → decode_chunks用同一规划器决定步骤
  → D2=D0 XOR D1 XOR D3 XOR L0
```

FastTT直接对外层四个输入做 XOR。对照模式的 local0 子编码器把 L0 重编号为4，看到 `want={2}, chunks={0:D0,1:D1,3:D3,4:L0}`。恢复后保留有效的0、1、2、3、10，两种模式都移除未填条目。

用 `bash coding_benchmark_lrc.sh 2048 20` 可在本机 Redis 下验证。`--use-minimum` 只给解码器选中的片，`--decode-only-erased` 把本例目标设为{2}，`--verify` 逐字节比较。日志会显示四个输入 `helpers=0,1,3,10`。

局部／全局由 `make_repair_plan(want,available)` 判断，Ceph不传策略标志：

| 情况 | FastTT模式的处理 |
| --- | --- |
| 单D2，输入{0,1,3,10} | 局部0只缺1片，局部恢复 |
| D0、D1，输入{2,3,4,5,6,7,8,10} | 用L0和G+联合求解，读8片 |
| D0、D1、D2同时缺失 | 用L0、G+和G−联合求解，读8片 |
| D0、L0都要恢复 | 先用G+恢复D0，再局部生成L0 |

读前_minimum_to_decode只把计划inputs交给上层；读后decode_chunks按实际chunks重新规划并执行steps。上层负责可用性、实际读写和缓冲管理，分组与校验方程由插件解释。

**少读不等于少分配。** 本例每片4KiB，四输入共16KiB；基类仍新分配其余8片的32KiB，工作表主片约48KiB，结束时清理不能消除之前的峰值。完整前台读还需要D4～D7，因此同样缺D2时通常读8片，而非4片。

## 5. 联合恢复与实现边界

| 函数 | 责任 |
| --- | --- |
| `layers_init()` | 层成员、子编码器与编号关系 |
| `encode_chunks()` | 重排缓冲，执行各层编码并映回 |
| `make_repair_plan()`、`choose_equations()` | 局部优先，随后为最多三个缺失数据片选独立校验方程 |
| `_minimum_to_decode()` | 将计划输入交给Ceph，落实少读 |
| `decode_chunks()` | 只用有效输入执行步骤，维护known并清理未填条目 |
| `recover_fasttt()` | 单方程直接移位 XOR，多方程分窗消元，两条路径都检查首尾一致性 |

对于 D0、D1，扣除已知贡献后，L0 给出 `S[t]=D0[t] XOR D1[t]`，G+ 给出 `R[t]=D0[t] XOR D1[t-1]`。从 `D1[-1]=0` 开始依次求 `D0[t]` 和 `D1[t]`，再检查尾部。通用实现用移位多项式表达这些消元步骤，直接使用 L0 或 L1。

### 单线程实现

每个 32B 符号用一条 AVX2 向量处理。论文中的优化在 LRC 里这样落地：

| 优化 | 代码怎样做 |
| --- | --- |
| EPM 擦除与校验映射 | 若 D0、D1、G+ 同时缺失，已知数据代入方程时也更新 G+，每解出一个 D0、D1 符号就补上对应贡献 |
| CFWP 缓存窗口划分 | 每窗 16 个符号。编码保留跨窗的 7 个校验符号，联合解码只把移位递推的余项带入下一窗 |
| NMA 相邻贡献合并 | `write_globals()` 读取一对相邻数据片，例如 D0、D1，复用这对向量更新 G+ 和 G− |
| TPS 遍历方式选择 | D2 局部修复把四个输入的同位置符号在寄存器中 XOR，一次写回。用一个全局方程时直接还原移位，多未知量时走分窗消元 |

两种 FastTT 模式当前都限于单机工具。性能实验使用 `fasttt-redis`，计时包含 Redis 与摘要开销。片内尾部模式保留为正确性参考。Redis 模式已验证等长分片，集群写入顺序、重启后的元数据可用性和清理仍待系统验证。

Ceph基类已通过项目补丁传播 `encode_chunks` 错误，并在失败时清理输出。Redis 写失败会使编码失败，读取缺键或校验失败会使所选联合解码路径返回错误。安装、验证记录和接续步骤见 [开发交接](agent/fasttt-handoff.md)。
