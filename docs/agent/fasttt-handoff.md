## 1. 持续更新协议：本文件必须怎样被维护

### 1.1 “自回归更新”的执行含义

这里指一个闭环：**读取当前交接状态 → 核验代码和证据 → 执行任务 → 将新事实、修正与下一步写回同一文件 → 下一次从更新后的文件继续。**

Markdown 文件本身不会在后台运行、监听代码变化、定时唤醒 agent 或自动写入。持续更新依靠正在工作的 agent 执行本节约定；更换 agent 或工作区时，随任务一并提供最新的本文件即可。突发退出前尚未落盘的内容无法由文档保证恢复，故应在有意义的小步骤后保存检查点。

目标是让单份文件保存**理解和接续工作所需的全部核心上下文**。关键算法、接口语义、修改内容、决策理由、复现命令和结果摘要须直接写入正文，不能用“见另一份文档／旧聊天／某个文件”代替。源码、二进制和大量原始输出无需全部复制进本文，但它们不可成为理解结论的唯一入口。

本文使用内部章节／任务／实验 ID，以及代码身份（仓库名、提交、仓库相对路径、类／函数和行为特征）定位。裸文件名如 `ErasureCodeTsx.cc` 相对 `TSX_ROOT`；`src/erasure-code/ErasureCode.cc`、`src/test/...` 等显式 Ceph 路径相对 `CEPH_ROOT`；`build` 角色不等于任意现存同名目录。命令中的 `TSX_ROOT`、`CEPH_ROOT`、`BUILD_ROOT` 在运行时识别，不能从旧机器路径或文档位置盲推。相对路径用于发现源码，核心理解直接保存在本文。

### 1.2 何时更新

出现以下事件后，在下一个安全检查点更新，不必等待整项里程碑结束：

- 用户／导师的目标、优先级、范围或验收标准变化。
- 完成可独立描述的代码修改；接口、内存布局、线程模型、尾部格式或构建方式变化。
- 得到影响后续判断的实验结果、定位结论或失败尝试。
- 重要假设得到证实或被推翻；做出、替换、撤回技术决策。
- 更换工作树、分支、提交、Ceph 版本或实验硬件／配置。
- 开始长时间运行任务，以及任务完成、失败或被中止。
- 上下文即将压缩、任务结束、暂停工作或交给其他 agent。

一次进展更新必须联动：**第 0 节快照、相关代码地图／方案、任务状态、实验或决策记录、第 12 节下一步与变更记录**。只追加一句“完成了”不算有效更新。

## 2. 项目目标、已有工作与范围

### 2.1 已有研究基础

`[历史记录，未复现]` 课题为“移位异或纠删码的高效实现研究”。以 Two-tone Shift-XOR 为对象，解决其工程实现中的重复内存访问、缓存局部性和解码／校验恢复问题，形成 FastTT，并集成到 Ceph v18.2.7。

已有四项优化：

| 优化 | 核心理解 | 后续改代码时应保留／复核的点 |
| --- | --- | --- |
| CFWP：缓存友好窗口划分 | 用小窗口提高局部性，并按首次访问初始化 | 移位让窗口存在覆盖范围；原解码的代入需领先消元一个窗口，不能简单把窗口同时执行 |
| NMA：相邻合并访问 | 在 AVX2 寄存器内先合并邻接贡献，减少校验读写 | 新的四校验内核和输出分工不能只看线程数，须比较是否丢失原有复用收益 |
| EPM：丢失－校验映射 | 统一恢复数据与校验，省去独立重编码／复制阶段 | 新局部校验不是自动纳入旧映射；必须核对输入、缓冲和恢复语义 |
| TPS：遍历模式选择 | 单擦除走纵向直接 XOR 快路径，避免一般消元 | 单擦除快不等于局部修复；原快路径仍使用全局方程所需的输入 |

`[历史记录，未复现]` 已有约 2000 行 C++、AVX2 实现，以及编码、解码、消融和 Ceph 端到端实验。既往结果中，编码相对 ISA-L 平均提升 59.1%，端到端 PUT 平均提升 7.1%，且存在两擦除及部分 `(10,4)` 多擦除不占优的情况。原实验的全部输入、运行参数与原始输出尚未在当前环境复核，因此这些数字只说明已有研究背景，不能作为当前代码性能承诺、M1／M2 加速目标或验收依据。

历史计划还包括优化机理验证和小规模覆盖写增量更新，总排期延续至 2027 年 5 月；另有从方案确认后起算的六周原型与系统验证设想。两者均未在本次修订中重新确认，不能把相对周数换算为新承诺日期。当前任务优先级按下一小节执行。

## 3. 独立理解所需的核心结论与证据边界

本节直接说明此前工作的关键理解；正文中的算法、代码职责和任务不要求读者打开其他文本。后续从任何来源获得新信息时，也应将会影响实现的事实与理由转述进正文，并说明是否实际核验。

| 核心结论 | 对代码工作的含义 | 当前证据边界 |
| --- | --- | --- |
| Shift-XOR 的主要瓶颈常是内存访问而不是 XOR 本身 | 优化要计量读写、暂存和缓存，不能只比较运算次数 | 已有参考代码行为与历史研究摘要；新方案仍待实测 |

## 4. 编码与数据语义：实现前必须吃透

### 4.1 Two-tone 基本运算

设数据片段为 `D_j`，校验为 `C_i`，移位矩阵为 `s[i,j]`。以一个 SIMD 单元为索引：

```text
C_i[t] = XOR_j D_j[t - s[i,j]]
```

越界输入按零处理。实现通常用地址偏移；这里是非循环移位，不能绕回片段开头。当前主线按 AVX2 的 256 bit＝32 byte 为单元；位、字节、32B 单元、片段、节点必须分别标注。

原解码总体为“已知数据代入 → Two-tone 逐次消元 → 必要的校验恢复”，FastTT 通过 EPM 等合并流程。逐次消元有前后依赖，不能因为 XOR 满足交换律便任意并发执行。

### 4.2 理论条件和现有实现须分别判断

CFWP 的设计条件是窗口至少覆盖 `k-1` 个单元；一种取值办法是选择满足该条件的最小二次幂。但历史参考代码实际上使用固定窗口，具体数值已在第 7 节写明。接手时须追到运行脚本实际选择的插件，不能假定存在自动调参，也不能只读一个同名类便代表全部变体。

### 4.3 内存与存储的共同不变量

- 明确逻辑对象长度、片段有效长度、SIMD 补齐长度、校验物理长度以及移位尾部长度。
- 不能用无符号索引直接计算 `t-shift` 后再判越界，避免下溢；先判断范围或使用受控有符号运算。
- 片段编号与磁盘／OSD 索引的映射须显式记录；下文的 `G+、G-、L0、L1` 是语义名称，尚未确定新池的序列化编号。
- 解码只能使用计划选中的可用片段；不可从测试仍持有的完整数据偷读。
- 输入／输出是否允许 alias、哪些缓冲会被原地修改必须写入接口。旧代入／EPM 可能改写工作校验；并行时应保持共享输入只读，或为改写区提供明确的私有 scratch 和依赖安排。
- 所有输出包含必要尾部，逐字节验证；零填充、对齐和边界字节不能靠上次缓冲残值。
- 异步任务结束之前，输入、输出、临时缓冲和上下文必须存活；Ceph 接口返回前必须完成相应任务和必要的可见性保证。

## 5. M1：局部冗余纠删码

本节定义完整TT-LRC目标。r16已实现独立插件骨架、局部XOR与ISA占位执行流，但G+/G-、移位尾部和完整三擦除恢复仍未实现，见7.18；覆盖写增量接口后置。

### 5.1 拟议布局与编码

```text
数据：D0 D1 D2 D3 | D4 D5 D6 D7
局部：L0          | L1
全局：G+，G-

L0[t] = D0[t] XOR D1[t] XOR D2[t] XOR D3[t]
L1[t] = D4[t] XOR D5[t] XOR D6[t] XOR D7[t]
G+[t] = XOR(j=0..7) D_j[t-j]
G-[t] = XOR(j=0..7) D_j[t-(7-j)]
P0[t] = L0[t] XOR L1[t] = XOR(j=0..7) D_j[t]
```

- 存储 12 片段：8 数据、2 移位全局、2 局部。原无移位全局校验 `P0` 不单独保存，需要时生成。
- 每个数据片段的非空规范化长度为 `B=32N` 字节时，本固定 8 列布局中 `L0、L1` 各长 `B` 字节，`G+、G-` 各长 `B+7×32=B+224` 字节，即各多 224 字节尾部。这里的 `B` 不是整个对象长度。非整单元或空输入须先定义补齐／有效长度语义，再据此计算实际尾部。
- 基础存储倍率从原 `11/8=1.375` 变为 `12/8=1.5`；尾部、对齐及元数据开销另计。
- 单数据片段丢失且本组其他四份可读时，只读本组其余 3 数据＋1 局部校验。例如 `D2=L0 XOR D0 XOR D1 XOR D3`。
- “读 4 片”是相应故障条件下的片段读取量。它不是任意故障的固定代价，也不等同于访问 4 台物理服务器。

### 5.2 容错声明与证明边界

`[代数推导]` 先定义 11 片段基码：8 条数据 `D0…D7` 加三条校验 `G+、P0、G-`，其中 `G+、G-` 使用第 5.1 节的公式，`P0= XOR(j=0..7) D_j`。本推导明确以该基码可恢复任意三片段擦除为前提，且所需移位尾部完整可用；r8已在原TSX两种对齐长度、constant/random输入上验证三擦除组合，但任意长度、独立显式尾部内核及新12片布局仍须分别验证。新布局可将至多三片段擦除映射回该基码恢复：

1. 两个局部校验均在时，生成虚拟 `P0=L0 XOR L1`，交回原 11 片段码处理数据／全局擦除。
2. 任一局部校验缺失时，将虚拟 `P0` 也标为缺失。新布局总擦除不超过 3，则原数据／移位全局擦除数加这一个虚拟缺失不超过 3；恢复数据后重新生成局部校验。

这是设计的条件性论证，仍须通过实际代码与尾部语义验证。**不保证任意四片段丢失，也不能在 12 片段中任取 8 片恢复。**

四擦除反例：`D0、D1、G+、G-` 同时丢失，只剩 `L0` 提供 `D0 XOR D1`，不能唯一确定二者。

这里的擦除指已知哪些片段不可用，不等同于定位未知的静默损坏。片段容错不能直接写成物理服务器容错：同一条带若一台机器放多片，整机失效会一次丢多片；必须核对 CRUSH／故障域／OSD 放置。

### 5.3 恢复计划与优化候选

`[当前Ceph18代码复核，2026-11-02]` `ErasureCodeTsx` 没有覆盖 `_minimum_to_decode()`；当前Ceph18基类在目标不全可读时要求至少k片并选编号顺序前k片，`minimum_to_decode_with_cost()`也仅转集合后走同一规则，没有按成本排序。因此 M1 必须同时实现**选片契约和恢复内核**：只改 `decode_chunks()`，既不能让 Ceph 用 4 片触发局部恢复，也不能防止 12 片布局选到不可解的 8 片集合。当前18的set/map接口与读路径约束以7.14为准；7.7仅保留历史20接口差异。

| 情况／候选 | 做法 | 需要证明或比较什么 |
| --- | --- | --- |
| 组内单数据擦除 | 读本组 3 数据＋局部校验，直接 XOR | 读取集合真实生效；避免 Ceph 仍把 8 片全部读入后才局部计算 |
| 单局部校验擦除 | 从该组 4 数据重算 | 恢复目标包含校验，片段长度／编号正确 |
| 全局或混合擦除 | 先生成合法恢复计划，再使用局部／全局方程 | 有足够片段不等于可解；恢复全部目标与尾部 |
| 四校验同算 | 同一次扫描更新 `G+、G-、L0、L1` | 与“两移位全局优化内核＋AVX2 局部 XOR”比较；地址／暂存开销可能抵消少一次扫描 |
| 按需生成 P0 | 恢复某段时即时从 `L0 XOR L1` 生成，避免完整临时 P0 的一写一读 | 不能只赢“先完整生成 P0”的简单接法，还要比较直接局部方程法 |
| 局部与移位联合恢复 | 对指定故障使用更少片段的合法方程 | 每个读取来源、边界、解码依赖和尾部都需写清 |

具体联合恢复例：仅 `D0、D1` 丢失，读 `D2…D7、L0、G+` 共 8 片：

```text
S[t] = L0[t] XOR D2[t] XOR D3[t] = D0[t] XOR D1[t]
R[t] = G+[t] XOR 已知列D2…D7的移位贡献 = D0[t] XOR D1[t-1]
D0[t] = R[t] XOR D1[t-1]       # D1[-1]=0
D1[t] = S[t] XOR D0[t]
```

上式计算 `t=0…N-1`，存在前后依赖；其他数据对须重新推导移位差和依赖链，不能照抄该递推。还应核对尾部约束，例如本例 `R[N]=D1[N-1]`。相比之下，用 `D2…D7、L0、L1、G+` 共 9 片拼虚拟 P0 是另一实现，不能把它当作唯一最优基线。

选片反例：`D4、G+、G-` 丢失时，`D5、D6、D7、L1` 即可恢复 D4；“7 个健康数据＋L0”不含足够 D4 信息。恢复计划应描述目标、输入集合、每段来源与策略，且测试仅提供这些输入。

## 6. M2：多线程模式设计

### 6.1 为什么不能直接按输入窗口分线程

`[代数推导]` 以 32B 单元为位置，八列偏移为 0…7，窗口 16 单元。任务 A 处理输入 `[0,16)`，任务 B 处理 `[16,32)`，各自向 G+ 更新的范围分别为 `[0,23)` 与 `[16,39)`，重叠 `[16,23)`。

例如 `D1[15]` 与 `D0[16]` 均更新 `G+[16]`。无同步的读－改－写 XOR 可能丢掉一份贡献。数学上的可交换性不能消除内存数据竞争。

### 6.2 优先实现的拥有权方案

`[设计建议]` 按校验输出范围分任务，每个输出地址有唯一写入者：

1. 任务拥有 `[begin,end)` 输出范围，尾部也分配明确拥有者。
2. 由输出索引减列移位，反向定位输入；越界按零。
3. 输入可被多个线程读取，输出和临时可写区不得无约定地共享；输出初始化也由拥有该范围的任务完成。
4. 所有输出区间构成完整、不相交覆盖，SIMD 宽存储也不得越过任务边界。边界按实际缓存行对齐，尽量使用足够大的任务，避免伪共享和调度开销。
5. 任务全部完成并满足所用存储指令的可见性要求后，才返回调用者。

单写者解决写竞争，但不自动解决解码的读后写依赖：任务仍可能读取另一任务尚未恢复的数据。此方案可能增加输入读取，并改变 NMA 的复用方式。因此至少比较“旧内核 1 线程、新内核 1 线程、新内核多线程”，分别衡量算法重写成本与并行收益。首批覆盖编码和单擦除；一般消元不能机械套用这套独立输出假设。

`[代码核验]` 这里的“旧内核”对应 `ErasureCodeTsx::encode_chunks()` 的 `window_id/chunk_idx/slice_id` 循环，以及 `decode_one_data_chunk()`；一般解码对应 `decode_chunks()` 中 `coding_data_map/need_decoded/maperasure_ptr` 和先代入窗口 `w`、再消元窗口 `w-1` 的循环。新任务应在明确缓冲契约的内核层引入，Redis SET／GET、连接使用和 Ceph 返回语义由外层请求负责。直接给现有 `window_id` 循环加并行指令不满足本节契约。

任务级／对象级并行可作为保留原 SIMD 内核的对照或过渡实现，但须与本节输出分工的研究目标分开记账。

### 6.3 线程池与请求分配

至少比较三个模式：每请求单线程、固定线程数、按请求大小及活跃请求数调整线程数。复用线程池，避免每次编码创建／销毁线程。

- 线程预算必须明确是否包含参与计算的调用线程、等待线程及后台线程。
- 建议将预算定义为同时参与编解码计算的线程上限，包含参与计算的调用线程；如预算为 4 且调用线程计算，最多再增加 3 条计算工作线程。等待／空闲线程另计。
- `floor(核心预算/活跃请求数)` 只是分配建议，活跃请求数会变化；实际上限必须由共享令牌、固定总池或等价机制执行约束，不能靠各请求独立估算保证。
- 单进程线程池不等于全机 OSD 共同限额。若宣称全机预算，要有跨 OSD 的静态配额或实际协调方式及证据。
- 单个大请求可利用空闲核；高并发请求应避免各开多个线程造成过量竞争。
- 调用线程持有线程池许可又等待子任务时，要分析池耗尽／嵌套提交死锁；任务必须有不会卡住的推进路径。
- 错误／取消路径同样要回收全部已提交任务：待其完成或确认停止后，才释放／复用 Ceph 缓冲和归还线程预算；不能首次遇错就提前返回，让后台任务继续访问已释放内存。
- 初始化、缓冲分配、Redis 连接、键生成、错误处理等副作用一并纳入线程安全检查。只让 XOR 内核无竞争不足以证明完整请求安全。
- 保留可用的一线程回退路径；块大小和并发阈值由实测决定，不把教学例的 8 核／4 线程写死为最优参数。

### 6.4 多擦除并行的边界

两擦除及更高擦除的逐次消元可能读取其他位置刚恢复的值，不能直接套用编码任务切片。分段并行若要成立，必须先推导每段所需的初始状态，再设计状态传递与结果修正；目前未确定适用于任意故障集合的一般方法，亦未验收实现。此方向后置，先保留顺序解码。特定故障上的历史 Python 等价性记录，不构成通用并行算法或加速证据；新增扫描、暂存与同步须计入成本。

- 主三校验实现固定 `Kval=8`、`Mval=3`、`SLICE=32`、`EXTRA_DATA_SIZE=224`；编码／解码窗口均为 **16 单元＝512B**。四校验变体编码窗口 16、解码窗口 **32**，另有 2 单元步长校验。
- 主编码器以 `blocksize/32/16` 的整除值遍历完整窗口，没有 remainder 循环；`get_chunk_size()` 只有向上除以 `k`。主编码的候选基线片长应取 512B 整数倍，仍须验证最小长度和解码边界；内存地址对齐不等于逻辑片长已补齐。单数据快路径虽不按 16 单元分窗，也仍只处理完整 32B 单元。
- `k,m` 可从 profile 读取，但 `init()` 未调用 `sanity_check_k_m()`；`m` 的运行时值与固定 `Mval=3` 数组／循环不统一。`chunk_idx+1` 成对加载不能安全支持奇数 `k`；固定尾部容量也限制可用 `k`。默认参数／脚本使用过的参数不能当作任意配置已通过。
- 主入口仅在“恰好 1 个数据缺失且 3 个校验都在输入集合”时调用单数据快路径；数据全在且只缺 1 校验时调用单校验重算；校验全缺而数据全在时复用编码器。数学上只需 7 数据＋P0，不代表当前分支条件允许只给这 8 片便走快路径；Ceph 实际选片与该条件的配合仍待实测。
- 一般解码先在当前窗口代入，再对前一窗口消元，具有“代入领先消元”的依赖；这不是自动可并行的独立窗口。
- 已读的 9 个非 Plugin 编解码实现（含 Cerasure 包装）中，未发现 OpenMP 指令、线程创建、线程池或实际异步执行标记；结论是**未见编解码多线程实现**，不是“链接 OpenMP 后已实现”。
- 原TSX主内核未见局部组／局部校验／locality 参数，校验遍历全 `k`；r16新增独立tsx_lrc骨架见7.18。Ceph 原生 lrc 模块被纳入构建，只说明那个模块存在，不代表 FastTT 已完成 M1。

### 7.4 Redis 尾部：当前实现、具体局限与改动入口

主三校验内核：

```text
encode_chunks：分配 448B parity_buffer，两个移位校验各用 224B。
encode_chunks：同步 SET，key = 无移位校验首32B内容，value = 448B尾部。
decode_chunks：window_id==1 时 GET，复制 reply->str/reply->len，再挂接 G± 的 extradata。
```

下面区分**方程的有效尾长**与**当前分配／SET 的容量**，二者不能混用：

| 插件／配置 | 由移位公式得到的有效尾长 | 现实现分配／Redis value 容量 |
| --- | --- | --- |
| `tsx` `(8,3)` | G+、G- 各 224B | 2×224＝448B |
| `tsx` `(6,3)` | G+、G- 各 160B | 宏仍为 2×224＝448B |
| `tsx2` 默认 `(6,2)` | 移位校验 160B；P0 无尾部 | 224B |
| `tsx4` 默认 `(10,4)` | 两个单步长校验各 288B；双步长校验 576B | 三槽各 704B，共 2112B |

本表来自默认／指定参数的静态偏移与容量核验；r8另有两种长度／两类输入的恢复测试，不能由该有限矩阵推定所有尾槽与边界已验收。未使用尾槽是否初始化、是否被错误地序列化／读取需要纳入边界检查。

上述 GET 描述针对一般窗口解码路径；单擦除快路径可提前返回，不能推定每次 `decode_chunks()` 都执行 Redis GET。计量同步 Redis 开销时应按实际分支区分。

需要接手 agent 明确处理的代码事实／待验证影响：

- 当前键来自数据相关内容，**不是对象 ID／条带 ID／版本号**。不同条带可能共享相同首 32B 校验却有不同尾部；跨对象覆盖、更新及并发时的实际故障表现尚未运行验证。
- `install_dependencies.sh` 关闭 Redis RDB／AOF 持久化。当前配置不能支持“尾部重启后可靠可读”的宣告。
- GET 后直接使用 `reply->str` 和 `reply->len`，缺少对空回复、错误类型、缺键和期望长度的检查，复制长度也未限制到分配容量。未来必须检查错误传播；当前父 Ceph 的旧 `encode()` 还丢弃 `encode_chunks()` 的返回值，只给内核加错误码不构成完整修复。
- `rctx` 作为实例成员；实例是否被并发调用、连接的使用方式和同步／连接池选择尚未核验。新增线程前先固定契约。
- 主编码的 `parity_buffer` 在返回前未释放；主一般解码有对应 `free`。`PadChunkPtr::unimportant` 分配后无析构释放；`tsx4` 解码尾缓冲的释放在关闭的 `ENABLE_LOG` 分支内。这些是静态释放路径发现，未测泄漏量。
- `ErasureCodeTsx` 构造函数没有初始化 `rctx`；`init()` 在参数解析失败时可早退，随后析构会检查该指针。`redisConnect()` 返回空指针的错误分支仍访问 `rctx->errstr`。应补初始化和错误路径，不将静态风险写成已经复现的崩溃。
- `ParityChunkPtr::operator[]` 没有尾部容量检查；`PadChunkPtr` 的越界目标是可写 sink，初始为零并不保证被写过后仍为零。这两个 helper 不能直接当作新内核的通用安全边界接口。
- 当前 GET 位置依赖窗口过程；短片段、P0 缺失、尾部缺失与新局部恢复路径都须重新验证。

M1 不再保存 P0，会直接触及旧“用 P0 首 32B 作键”的耦合；不能只新增 L0／L1 后保持全部尾部逻辑不变。独立原型可先把尾部作为显式输入／输出，Ceph 接入时再落实对象／条带／版本一致的可靠方案。选择何种存储方式尚未确定，不能将建议伪装成已有接口。

### 7.7 历史 Ceph20 接口差距与读取计划（18基线不适用）

`[历史代码核验／静态推论，未编译]` 以下仅对应 r3 时 Ceph20；r8 已切回18，这四项新纯虚要求不再是当前阻碍。历史 Ceph 的 `ErasureCodeInterface.h` 要求下列纯虚方法，`ErasureCode.h` 与 TSX 主类都没有提供这些实现：

```text
get_minimum_granularity()
encode_chunks(const shard_id_map<bufferptr>& in, shard_id_map<bufferptr>& out)
decode_chunks(const shard_id_set& want_to_read,
              shard_id_map<bufferptr>& in, shard_id_map<bufferptr>& out)
get_supported_optimizations() const
```

当前 `ErasureCodeTsx.h` 只覆盖旧 `std::set<int>/std::map<int,bufferlist>` 编解码方法。因此在这套 Ceph 中，`ErasureCodePluginTsx::factory()` 的 `new ErasureCodeTsx` 无法满足完整接口；这是源码可判定的抽象类问题，不是本轮编译器报错记录。其他变体也要逐一检查。

当前 Ceph `ErasureCode::encode()`／`_decode()` 的新接口路径实际调用新的 `bufferptr` 版内核。只补空方法或任意返回“支持优化”不能完成适配：需要定义各 shard 输入／输出的含义、长度、别名、缺省输入及错误传播，再复用或改写内核。`get_supported_optimizations()` 只能报告真实实现的能力；不能因接口存在便开启增量更新，基类的 `encode_delta/apply_delta` 默认实现会中止。

读片入口有两套 `_minimum_to_decode` 重载。当前基类先检查目标是否全可读；否则要求可用片数至少为 `k`，取排序前 `k` 片。两套成本入口也只是转换可用集合后转调，未利用成本。TSX 未覆盖这些规则。M1 应让读取计划、实际传给解码器的集合和恢复策略保持一致，测试中剥离未选片段；不得依赖基准程序仍持有的其他幸存片触发 TPS。

**历史T0分支选择已解决。** 用户已确定并完成官方Ceph18.2.7＋普通AVX2回归，四项Ceph20新纯虚适配不属于当前工作。新build来源和限定正确性已验证，不能把旧AVX512归档重新作为基线。

### 7.9 官方 LRC：配置、分层实现与通用接口

`[官方文档＋本地代码核验，2026-10-29，E-LRC-r4]` 用户要求先完成实现基础的理解。本节以内联案例记录结果，不代表已配置或运行官方 LRC 池。本节为历史Ceph20核验，源码身份 `v20.2.0@69f84cc2651aa259a15bc192ddaabd3baba07489`；当前18的通用LRC结论与接口／OSD差异见7.14，特别是新bufferptr、flags和优化池段落不可套用到18；官网 `en/latest` 明确属于开发版本，因此同时对照 `en/tentacle` 与当前源码，版本差异不能忽略。

**配置与参数。** 以下是讲解用命令，未执行；`stripe_unit=4K` 用来明确后面的单条带大小：

```bash
ceph osd erasure-code-profile set lrc_demo \
  plugin=lrc k=4 m=2 l=3 stripe_unit=4K crush-failure-domain=host
ceph osd pool create lrc_demo_pool erasure lrc_demo
ceph osd erasure-code-profile get lrc_demo
ceph osd pool get lrc_demo_pool size
ceph osd pool get lrc_demo_pool min_size
```

`k=4` 为原始数据片数，`m=2` 为全局基码校验数，`l=3` 表示把这 `k+m=6` 片按每 3 片分组，每组再增加 1 片局部校验。组数 `g=(k+m)/l=2`，最终 `n=k+m+g=8` 片，所有校验合计 4 片；不能把 profile 的 m 与接口返回的 `get_coding_chunk_count()=n-k` 混用。每片 4KiB 时，一条原始 16KiB stripe 对应 32KiB 片段数据；普通 RS 4＋2 为 24KiB，均未计元数据等开销。多条带对象不是整对象只拆一次。

`ErasureCodeLrc::parse_kml()` 自动生成下面的物理编号；`TestErasureCodeLrc::parse_kml` 对字符串有逐字断言。官方手写低层示例使用另一套等价布局编号，不能与本表的擦除位置混用。

```text
chunk ID       0 1 2 3 4 5 6 7
mapping        D D _ _ D D _ _      原始数据在 0,1,4,5
global layer   D D c _ D D c _      全局校验在 2,6
local layer0   D D D c _ _ _ _      局部校验在 3
local layer1   _ _ _ _ D D D c      局部校验在 7
语义内容       D0 D1 G0 L0 | D2 D3 G1 L1
```

这里 `mapping` 的 D 标出原始数据位置；每层字符串的 D 是**这一层的输入**，可以是上一层生成的校验；c 是这一层生成的输出，`_` 不参与该层。相应低层配置为 `mapping=DD__DD__`、三层 `DDc_DDc_`／`DDDc____`／`____DDDc`。高层 `k/m/l` 会生成它们，不能再同时手写 `mapping/layers/crush-steps`。

**编码与恢复。** `layers_init()` 从每层的 D/c 计算子插件 k/m，默认实例化 `isa/reed_sol_van`；全局层是 4＋2，两局部层分别为 3＋1。编码按层正序执行。默认 ISA 的 `m==1` 分支直接 XOR，因此 `L0=D0 XOR D1 XOR G0`，`L1=D2 XOR D3 XOR G1`。局部组含全局校验，这与 M1 的数据组局部校验不同。

| 本表编号下的故障／目标 | 恢复规划与所需输入 |
| --- | --- |
| 只丢 chunk 0，目标 `{0}` | 选 `{1,2,3}`，即 D1、G0、L0，计算 `D0=L0 XOR D1 XOR G0`；每片 4KiB 时读 12KiB，普通 RS 单片恢复通常需 4 片＝16KiB。这是字节量推算，未实测 |
| 丢 chunk 0、1，目标 `{0,1}` | 局部层缺 2 片超过该层 1 校验能力，跳过；全局层用 `{2,4,5,6}`，即 G0、D2、D3、G1，恢复两数据 |
| 丢 chunk 0、1、2 | 局部层缺 3＞1，全局层缺 3＞2，规划器返回 `-EIO`。总共 4 个校验不等于任意丢 4 片可恢复 |

`_minimum_to_decode()` 和 `decode_chunks()` 都逆序查看局部层、再尝试全局层；后恢复的片可用于其他层。选片是层次启发式，复杂后备路径会返回全部可用片，不能称为任意故障下的全局最少读取算法。“读 3 片”只针对相应目标片的恢复；完整对象读还需其他数据，读取全对象时不得直接沿用这个计数。正常读取目标全可用时直接读取目标，不必解码。

**官方支持的接口位置。** `ErasureCodeLrc` 继承通用 `ceph::ErasureCode`／`ErasureCodeInterface`，没有另起一个仅供 LRC 的基类。profile 的 l 是该插件解释的参数，给 `plugin=tsx` 增加 l 不会自动获得局部冗余。

| 现有接口／代码锚点 | 对局部冗余的作用 |
| --- | --- |
| `get_chunk_count/get_data_chunk_count/get_chunk_mapping` | 返回实际总片数、原始数据片数和逻辑至物理编号映射；允许局部校验额外占片 |
| `ErasureCodeLrc::parse_kml/layers_init` | 将高层参数转为布局／层，实例化每层子插件；子插件只处理本层连续编号的输入输出 |
| `encode_chunks/decode_chunks` | 实际生成校验与恢复字节；历史20同时保留旧接口和新bufferptr接口；当前18仅set/map接口 |
| `minimum_to_decode → Lrc::_minimum_to_decode` | 根据目标和可用集合决定要读哪些片；是让局部修复减少真实读取的关键入口 |
| `create_rule` | 生成 CRUSH 放置规则，将数学分组映射到故障域／拓扑 |

历史20普通LRC池的真实读片链是（当前18对应ECBackend，见7.14） `ECCommonL::ReadPipeline::get_min_avail_to_read_shards → minimum_to_decode(want,have) → need → pg_shard/OSD to_read → 读取 → 解码`。`ECCommonL.cc` 在调用后按 need 构造 to_read；恢复时禁止额外冗余读。插件不自己发送网络请求，也不是先读全部片再只挑几片计算。

**拓扑、服务门槛与版本限制。**

- 默认 `crush-failure-domain=host` 时，本例 8 片放不同 host；需要足够的可放置故障域。`crush-locality=rack` 则生成 `choose rack 2`＋`chooseleaf host 4`，两个四片组分别在两个 rack，各组内跨四个 host。它不改变校验方程，也不保证整 rack 故障可恢复；跨 rack 流量还取决于 primary／恢复执行位置。
- `OSDMonitor::prepare_pool_size()` 以插件返回值设置 `size=8`，默认 `min_size=k+min(1,coding_count-1)=5`。min_size 是池的服务／活跃门槛，与某次恢复的 3 个 helpers 不同；可解性也不能只靠存活片数判断。
- 当前高层参数除 `(k+m)%l==0` 外，还要求 `g` 分别整除 k 和 m。官方简介中的 `k=8,m=4,l=4` 在本地源码会因 `8%3!=0` 被拒；这属于文档／源码的静态差异，未实际执行 CLI。以当前代码及单测支持的 4／2／3 为讲解基线。
- 局部修复无需设置 `allow_ec_optimizations`。历史20的LRC虽实现新bufferptr接口及部分能力位，却缺少 `FLAG_EC_PLUGIN_OPTIMIZED_SUPPORTED`；`OSDMonitor::enable_pool_ec_optimizations()` 因而拒绝启用新优化池。新接口完整性和优化池可用性是不同层次，不能由部分 flags 推断已受支持。

**对 M1 的可用结论与未决实现。** 可以借鉴官方分层框架，也可以让 TSX 直接实现相同的通用接口；尚未选择架构。`k=8,m=2,l=5` 虽同为 12 片，但局部组为 4 数据＋1 全局＋1 局部，单片恢复读 5 片，并不是 M1 的读 4 片布局。M1 在低层字符串上可候选表达为 `mapping=DDDDDDDD____`、全局 `DDDDDDDDcc__`、局部 `DDDD______c_` 与 `____DDDD___c`；全局层必须另有真正的 G+/G− 实现和尾部契约。当前 `tsx2` 是 G+ 与 P0，不能直接替代，更不能把这一候选写成已经接入。

### 7.10 FastTT-LRC 最小原型：类比 ISA→TSX 的实现路径

`[历史设计建议＋代码核验，2026-10-31，E-PROTO-r5；r16实际骨架见7.18]` 用户要求先讲清最小实现逻辑，并未要求本轮创建插件。下面均为拟议名称与职责，不是已有文件／函数，也不代表已选定最终架构或已完成M1。r11已将最小接口表改为当前Ceph18要求，保留后文20缓冲分析的历史身份。

**与此前实现方式的类比。** ISA→TSX 可沿用 Ceph 插件注册、factory、profile 和构建骨架，编解码处接入 TT 算法；TSX→TSX-LRC 可沿用同类骨架，复用 TT 计算，再增加局部组、局部 XOR 和恢复分派。新增的关键责任是 `_minimum_to_decode()`：选片必须与实际恢复算法配套，不能继续使用默认任取 k 片规则。官方 LRC 提供这一组织方式的参照，不必初版就复制它的通用 JSON layers／参数生成器。

当前 `ErasureCodeTsx` 与 `ErasureCodeLrc` 都声明为 `final`，不能直接派生。建议先建立 `ErasureCodeTsxLrc : public ceph::ErasureCode`，通过独立函数／组合对象复用算法。可拟议新增 `ErasureCodeTsxLrc.h/.cc`、`ErasureCodePluginTsxLrc.h/.cc`，在 TSX CMake 中增加 `ec_tsx_lrc` 共享库目标，由 factory 创建新类。内部帮助函数初期可放在同一 `.cc`；需要复用时再抽出独立内核文件。原 main 保持可识别的基线。

**固定一个布局先贯通。** 保留第 5 节的 8＋2 全局＋2 局部目标，原型候选编号为数据 `0…7`、G+ 为 8、G- 为 9、L0 为 10、L1 为 11。`L0=XOR(D0…D3)`，`L1=XOR(D4…D7)`；原 P0 不落盘。先固定 k＝8、总片数＝12、数据局部组大小＝4，拒绝不支持的 profile／mapping。该物理编号尚未形成已实现存储格式；不要改写第 5 节的未确定状态为“已经发布”。

最初的内存原型可只接收 B＝4096B 的规范化数据片以避开长度调参；有效长度和零填充必须明确。Stripe 显式包含 8 条 B 数据、G+/G- 各 B＋224B、L0/L1 各 B，不依赖隐式 Redis 查键取得计算所需字节。之后再扩大长度与参数范围。

**三个核心动作。**

| 动作／拟议入口 | 第一版职责 |
| --- | --- |
| `encode_core()` | 调用适配后的 TT 编码得到 G+、临时 P0、G- 与完整尾部，再分别 XOR 两组数据得到 L0/L1；暂时多算 P0 可以接受，正确后再融合／去掉冗余计算 |
| `make_repair_plan(want, available)` | 返回策略、真实输入集合、目标与所需中间量；先判断目标已在、再判断局部可恢复，最后尝试已支持的全局后备；不能恢复则返回错误 |
| `decode_core(plan, inputs, outputs)` | 严格只用选中输入执行对应策略，只保证指定目标完成；未知片和缺失尾部不能当作零或假装已知 |

同一个规划逻辑服务 `_minimum_to_decode()` 和解码，避免各写一套条件后不一致。计划使用请求局部状态；不要把上一次请求的计划缓存在插件实例中。最小局部例子：目标 D2／片 2 缺失，输入 `{0,1,3,10}` 可用，则只读 D0、D1、D3、L0，计算 `D2=L0 XOR D0 XOR D1 XOR D3`。目标 L0 时读取数据 `{0,1,2,3}` 重算。复杂多目标尚未支持时明确拒绝，不把部分目标恢复当作整个请求成功。

局部 XOR 初版可用逐字节四输入循环，之后再换 AVX2；当前 `decode_one_data_chunk()` 按实例 k 遍历，默认 k＝8，不能直接把四个组内指针交给它。可抽取接受输入数量的通用 XOR helper，或单独实现四输入局部函数。

**复用 TT 全局恢复的适配层。** 为旧 8＋3 逻辑建立临时视图 `[D0…D7,G+,P0,G-]`。两局部校验均可用时构造 `P0=L0 XOR L1`，不新增持久片。新物理 G- 的编号 9 对应旧临时视图编号 10，旧编号 9 留给临时 P0，不能直接混用两套索引。

初版全局后备可以读取全部健康片，并先只承诺经过验证的故障集合；可先限制在两局部均可用的场景，验证如 D0／D1 同组双擦除。更一般的第 5.2 节投影要求：局部缺失时 P0 也标为缺失而不是置零；是否支持由恢复内核实际能力决定。旧基码在r8的有限长度／输入矩阵已通过；一般性、显式尾部内核与新布局投影仍是独立验收前提，不因包装就宣告完成。

当前旧 `ErasureCodeTsx::decode_chunks()` 用 `chunks` 判断存在性，却从 `decoded` 取全部数据／校验指针；适配时需建立完整 11 片私有工作缓冲、拷贝已知输入并为缺片分配空间。局部修复的 4 片不能直接送入旧一般解码器，后者按固定三擦除数组处理过多“缺失”会不安全。一般路径还在窗口 1 用 P0 内容键查询 Redis，应把 TT 计算抽成显式尾部输入的内核，而不是直接调用旧插件就认为复用完成。现 Ceph `_decode()` 会给所有未读取片分配 out；out 中的片未必真的故障，不能用 out 的数量判故障。内核可以只计算 want 所要求的目标，但 Ceph 适配层只能向外发布已知有效／已完成的片；如复用基类全量预分配，需要覆写 decode／_decode 桥接或裁去外层 decoded map 中未完成条目。仅从 bufferptr out 删除条目不会自动删除外层 bufferlist map，不能把未初始化的额外片作为可用结果返回。

**Ceph 接口外壳的最小范围。**

| 职责 | 最小处理 |
| --- | --- |
| `init()`，片数／片长 | 校验固定配置，规范化后调用基类初始化；`get_data_chunk_count=8`、`get_chunk_count=12`，基类可推得校验片数为 4；片长按真实存储契约实现 |
| `encode_chunks/decode_chunks` | 当前18只需set/map版本，可转同一套内核适配；不实现历史20的shard_id_map/bufferptr重载 |
| `_minimum_to_decode(want,available,set*)` | 当前18覆写此set版本并转共享规划；基类minimum_to_decode及成本包装可复用，但不能继承默认任取k片策略 |
| 历史20 granularity/optimization接口 | 当前18不存在这些必需方法，不为本轮新增空接口；仍须自行定义真实粒度与支持边界 |
| 映射、CRUSH、subchunks | 初版采用数据在前的 identity mapping、单 subchunk，可沿用基类普通 host 放置规则；不需要一开始就做 rack 分组和通用 layers |
| `encode()` 包装与错误 | 当前18基类encode仍丢弃encode_chunks返回值；准备缓冲可借鉴，但需checked adapter／覆写或修复以传播错误。当前上层是ECUtil，完整系统错误链仍待核验 |

**先后次序与简化边界。** T0-A兼容基线已完成；按最新用户要求先完成T0-PAPER论文复现，再处理尾部／边界，之后完成固定内存Stripe编码、仅4输入局部恢复与已支持全局后备，再接factory、Ceph缓冲与实际读片路径；按每一层记录已实现／已通过状态。先完成内存内核只可标为“内核原型”，不能标为 Ceph 池可用。

可以暂缓多线程、校验融合、最优选片、任意 k/m/l、增量更新和 CRUSH 拓扑优化；目标字节正确、选片与恢复一致、必要尾部可用、失败不伪成功属于最小契约。初版通过编码／局部恢复／一个全局后备场景仍不等于 M1 的 298 种擦除与 M3 系统验收全部完成。

**接入 Ceph 时必须处理的长度事实。** 基类 `encode_prepare()` 按 `get_chunk_size()` 切分原始数据，当前18的`ECUtil`（历史20为ECUtilL）按 `stripe_width/k` 定义片长并断言编码后各片等长，Monitor 对显式 stripe_unit 也校验两者一致。简单把 get_chunk_size 改成 `ceil(raw/8)+224` 会连原始数据边界一同改变，移位仍会产生新的尾部，并没有解决尾部存储。内存原型可先用显式尾部；Ceph 版需单独确定逻辑数据映射、等长 shard 序列化／尾部存储及 I/O 偏移契约，当前尚未设计完成。

### 7.11 数据与校验混合分组，还是只对数据分组

`[代码核验＋代数分析，2026-11-01，E-LAYOUT-r6]` 这里比较的是官方 LRC 高层 k/m/l 的自动布局与 M1；Ceph 接口本身不强制把全局校验纳入局部组，手写 layers 也可以表达仅数据的局部组。不要把布局选择误说成接口限制。

为避免将此前官方 4／2／3 与 M1 的规模差异误当成分组收益，统一使用 8 数据＋2 全局＋2 局部。官方高层可取 k＝8、m＝2、l＝5；每组为 4 数据＋1 全局＋1 局部，共 6 片。记 `A=XOR(D0…D3)`、`B=XOR(D4…D7)`：

```text
混合组局部：U0=A XOR G0，U1=B XOR G1
数据组局部：L0=A，L1=B
```

| 项目 | 混合分组的直接／现成分层路径 | M1 数据分组的直接路径 |
| --- | --- | --- |
| 单数据恢复 | 其余 3 数据＋配对 G＋U，共 5 个 helper | 其余 3 数据＋L，共 4 个 helper |
| 配对全局校验恢复 | 4 数据＋U，共 5 个 helper；全局校验也有组内恢复通道 | G+/G- 没有同样的局部组方程；保守方案从 8 数据重算，其他输入组合需单独规划 |
| 局部校验重算 | 4 数据＋G，共 5 个输入 | 4 数据 |
| 编码执行依赖 | 当前层次实现先得到 G，再供局部层使用 | L 只依赖数据，可与 G 独立计算／融合访存 |
| 与 M1 的 P0 桥接 | 通用式为 `P0=U0 XOR U1 XOR G0 XOR G1`，不再只靠两个局部片 | `P0=L0 XOR L1`，即使某个移位全局缺失，两个 L 仍可直接给出虚拟 P0 |

表中的 helper 数是所列恢复路径，不是任意编码矩阵下的绝对下界；也不说明完整对象请求一定只读这些片。原生 LRC 默认全局是 RS，M1 全局是 TT G+/G-，二者方程不同，不能把性能／容错差异全部归因于分组。

特别地，默认 RS 的第一个全局校验为 `G0=A XOR B`，于是混合局部 `U0=A XOR G0=B`，可出现跨组代数简化或抵消。它说明“局部式多含一个 G”不等于多一份独立信息，配置路径也未必已经发现全部更小输入集合。覆盖写所需更新的片数／范围同样取决于系数与移位，不能一概宣称混合分组每次必改 4 校验，而数据分组只改 3 校验。

两种完整码字的局部片可以通过 G 做可逆代换，但擦除分布不保持；数据／校验如何分组不能单独决定谁的容错更强。M1 第 5.2 节的三擦除论证仍以 TT 三校验基码可恢复为前提；混合分组不能直接继承该虚拟 P0 证明，也不能因此就判定它一定更弱。

若保持 TT 的完整全局尾部后再作混合 XOR，应把 B 长数据零扩展到全局的 B＋224B；对应 U 也需覆盖这段尾部。两全局＋两混合局部的有效尾部合计 896B，而 M1 只有两全局携带尾部，共 448B。这是该具体构造的长度推导；若另定义尾部格式需重新计算。相同 12 片数不等于完全相同物理字节，Ceph 等长片适配仍按 7.10 待设计。

当前 M1 取舍主要针对数据修复输入少、P0 可由两局部片直接得到，以及数据局部没有移位尾部；全局校验的低读取量修复通道需要另做优化。没有据此宣称整体吞吐、系统延迟或任意故障可靠性已经优于官方 LRC。

### 7.12 Ceph 如何为局部校验准备内存并传给插件

`[本地代码核验，2026-11-01，E-BUFFER-r6]` 以下针对父 Ceph 20.2.0 固定提交；尚未实现的 M1 只作接口示意。Ceph 没有独立的“LRC 额外内存指针”参数；局部校验与全局校验通过同一批 shard 容器传入。配置 l 决定布局，片数接口决定准备多少输出，编解码参数携带具体字节缓冲，选片接口决定读取集合。

**编码准备链。** `ErasureCode::encode()` 调用 `encode_prepare()`，读取 `k=get_data_chunk_count()`、`n=get_chunk_count()`、`B=get_chunk_size(raw.length())`。基类对 k 条数据用 `substr_of` 引用原输入范围，必要时重建为连续对齐缓冲，不足部分复制／补零；不能说每次都重新分配 k 份完整数据。随后对 `n-k` 条校验分别执行 `buffer::create_aligned(B,SIMD_ALIGN)`，当前 SIMD_ALIGN＝64。此处已为局部校验准备空间，数据值由插件负责初始化和计算。

官方 4／2／3、原输入 16KiB、B＝4096B 的具体例子：

```text
物理编号：0  1  2  3  4  5  6  7
内容：   D0 D1 G0 L0 D2 D3 G1 L1
chunk_mapping=[0,1,4,5,2,3,6,7]
数据准备位置：0,1,4,5
校验分配位置：2,3,6,7，每个 4096B，共 16384B 校验 payload
```

这里用于循环的校验数为 `n-k=8-4=4`，不是 profile 中仅表示全局校验数的 m＝2。`get_chunk_count()` 由 LRC 的 mapping 长度得到 n；`ErasureCode::to_mapping()` 将原始数据位置列在前面，随后列出校验位置，供 `chunk_index()` 在分配和传参时映射到物理 ID。

| 外部接口 | 目标／编号参数 | 真正携带缓冲的参数 |
| --- | --- | --- |
| 旧 `encode_chunks(want_to_encode, encoded)` | want 集合表示希望保留的输出编号，不携带 payload | `std::map<int,bufferlist>* encoded` 同时含已有数据和已分配的校验缓冲 |
| 新 `encode_chunks(in, out)` | map 的 key 为 shard ID | `in` 引用数据缓冲，`out` 引用已准备的校验缓冲；都是 bufferptr 容器 |
| 旧 `decode_chunks(want_to_read, chunks, decoded)` | want 为必须恢复／返回的目标 | chunks 为实际已读片；decoded 含已知缓冲与新分配的恢复空间 |
| 新 `decode_chunks(want_to_read, in, out)` | want 为必须完成的目标 | in 为可用输入，out 承载预分配的恢复缓冲；结果只能发布已完成／已知有效的片 |

新基类 encode 包装先取完整 encoded 中每片的 bufferptr，按原始逻辑编号是否小于 k 放入 in_shards 或 out_shards，再调用新 encode_chunks。bufferptr 是对原有 raw buffer 的引用；容器复制／赋值通常增加引用计数，不复制整片 payload。`shard_id_map<bufferptr>(n)` 只创建容器槽位容量，初始 size 为 0，并不分配 n 个 B 字节缓冲；真正 payload 分配发生在 create_aligned 等调用处。

**TSX set/map接口的直接对应（当前18可用；下述bufferptr为历史20补充）。** 拟议 M1 采用 identity mapping 且 get_chunk_count＝12 时，encoded 中应先准备数据 0…7 和校验 8…11，局部输出就在 `(*encoded)[10]`／`(*encoded)[11]`。旧接口可取其 c_str() 写入 B 字节；新接口对应 `out[shard_id_t(10)]`／11 的 bufferptr。前提是条目和空间已准备；map 的 operator[] 遇到不存在编号只会创建空条目，不能拿它替代 payload 分配。校验缓冲不保证预先为零，第一次写要初始化／赋值，不能对未初始化内容直接 XOR 累加。

**LRC 分层复用同一批内存。** 全局层的 `layer.chunks=[0,1,4,5,2,6]` 被解释为本层连续编号 `[D,D,D,D,c,c]`；随后局部层 `[0,1,2,3]` 被解释为 `[D,D,D,c]`。物理 2 的 G0 已由前一层写入，下一层直接读取该缓冲再写物理 3 的 L0。

旧 LRC 通过 swap 把 bufferlist 暂时重排进 layer_encoded，调用后交换回来；新 LRC 复制 bufferptr 引用到 layer_in/out，没有为每一层额外复制完整片。具体实现还有一处命名细节：新局部层的 G0 来自最外层 out，因此处在 layer_out[2]；它在这一层仍是逻辑数据输入，真正新校验在 layer_out[3]。默认 ISA 同时从两个容器填入指针数组，再按本层 k＝3 区分前三条输入与后续校验输出；不能把 layer_out 名字理解成每一个条目都要被这一层覆盖。

**读取和解码链。** `minimum_to_decode(want, available)` 及 LRC 覆写的 `_minimum_to_decode()` 只返回输入 ID／subchunk 范围，不分配局部输出或自行发网络请求。`ECCommonL::ReadPipeline` 根据 need 构造实际 to_read。片读回后，基类 `_decode()` 对未出现在 chunks 的 ID 准备恢复空间，再转入旧 decoded 或新 in/out。只读 M1 的 `{0,1,3,10}` 恢复 D2 时，其他未选片也可能被基类分配 out，它们不等于真实故障；外层结果裁剪／有效性要求继续遵守 7.10。

**三类空间要分开。** 一是 Ceph 根据 n/k/B 准备并由 encoded/out 传入的持久 shard 主片；二是插件自己分配的算法 scratch，如临时 P0／私有消元缓冲；三是 TT 编码必须保留的有效尾部。当前 TSX 的 448B parity_buffer 在其 encode_chunks 内另行 aligned_alloc，不是 Ceph 自动替它分配的局部校验空间。把 n 改成 12 会增加主片条目，不会自动生成临时 P0，也不会自动给 G+/G- 各增加 224B 尾部或把这些尾部持久化。例示 raw＝32KiB、B＝4096B 时，通用准备器仅给 M1 四校验各分配 4096B 主片，系统接入仍受 7.10 的长度契约约束。

上述主片先在内存中准备，插件填写后由 OSD 写入相应 shard 对象；分配成功不等于已经持久化，bufferptr 本身也不是磁盘地址。

### 7.13 LRC 的接口职责、故障检测与两种恢复完成点

`[官方说明＋本地代码核验，2026-11-01，E-LIFECYCLE-r7]` 以下仍对应父 Ceph 20.2.0 固定提交；普通 LRC 以 legacy EC 路径为主要源码证据。本节解释机制，未在当前环境实际停止 OSD 或执行恢复。

**没有单独的 LRC 运行时接口。** LRC 使用通用纠删码接口。数学上的局部性来自布局和校验方程，`encode_chunks()` 写出这些方程的结果；`minimum_to_decode()`／子类 `_minimum_to_decode()` 把局部性转为少量真实读取；`decode_chunks()` 根据所选输入恢复目标。因此 minimum_to_decode 是减少 helper 读取的关键系统入口，但不是局部码存在的全部条件，也不负责故障监控、恢复调度或持久写回。只改变返回的片段集合而不匹配编码／解码方程不能得到正确 LRC。

**“不可用／缺失”的发现分不同层次。**

| 场景 | 主要发现途径 | 结论边界 |
| --- | --- | --- |
| OSD、主机掉线或网络不可达 | 同伴心跳检查、向 Monitor 上报，Monitor 根据报告／grace 更新 OSDMap | down 表示不可达，不是证明磁盘字节已永久丢失；不必先有对象读取 |
| 对象片缺失、版本落后 | peering 对齐 PG 历史与 missing 集合，或实际对象读取返回缺失／I/O 错误，scrub 也可发现 | missing 还可以表示版本落后；peering 不是逐字节扫描所有对象 |
| OSD 活着而数据静默损坏 | 实际读时的存储校验和检查，或主动 deep scrub 读数据校验 | 心跳不能发现这种内容错误；未访问的损坏可能等到 scrub 才暴露 |

普通 scrub 主要检查存在性／元数据等一致性，deep scrub 实际读取并检查数据。检出不一致并不保证立即自动修好；是否自动修复取决于配置、错误规模和能否确定正确来源，也可能需要 repair 工作流。局部码插件通常接收已经判定可用的片段及已知目标，不承担定位未知静默错误的功能。

心跳入口为 `OSD::heartbeat_check()`，异常 peer 入 failure_queue，`send_failures()` 发送报告，`OSDMonitor::check_failure()` 判断并更新 OSDMap。PG 根据新状态 peering，`PeeringState` 构建 missing／恢复源，`PG::queue_recovery()` 与 `PrimaryLogPG::start_recovery_ops()` 调度恢复。后台可运行而无需客户端读取该对象。

`down` 与 `out` 不同：out 是后续放置／迁移决策，可能使新目标接管；原 OSD 返回后也可能只需补齐旧版本。具体开始时间取决于心跳阈值、状态传播、peering、有效恢复源和目标、恢复 reservations／队列、资源与控制标志，不能用一个固定秒数概括所有恢复，也不能说所有恢复都先等待 down→out 的同一个超时。客户端受 min_size 等服务门槛约束，与后台恢复条件不同；PG 可以 peered 但暂不能服务客户端，同时进行恢复。

**内存解码与持久重建是两个完成点。**

| 流程 | 请求的目标 | 选片与计算 | 完成后的去向 |
| --- | --- | --- | --- |
| 可服务的普通降级读 | 本次客户端请求所需数据 | 根据 want/have 选 helper；缺目标时在内存中重构 | 裁剪为请求范围并返回客户端；这条解码回调自身不写缺失 shard |
| recovery／backfill 的片段重建 | missing_on_shards 中缺失或落后的数据／校验 | 后台按目标选 helper、读回并重构需要的片 | 将恢复字节推送至目标 OSD、提交存储事务、确认后更新恢复状态 |

两者都可能调用 minimum_to_decode 与解码算法。区别在于上层目的和结果处理，不能把“调用 decode”当作“已经修复磁盘”。如果同编号正确片本就有可用来源，也可能直接利用它，而不需要数学消元。

当前 legacy 普通读的具体链是 `ECBackendL::objects_read_async → ECCommonL::ReadPipeline::objects_read_and_reconstruct → get_min_avail_to_read_shards(for_recovery=false) → minimum_to_decode → ClientReadCompleter::finish_single_request → ECUtilL::decode/decode_concat → 截取请求范围 → complete_object → 请求回调`。`ClientReadCompleter` 将结果交给客户端，没有在这条链创建 recovery Push 或提交恢复写事务。

后台链是 `PrimaryLogPG::start_recovery_ops → recover_primary/recover_replicas → backend recover_object → ECBackendL::RecoveryBackend::continue_recovery_op`。其 IDLE 状态以 `for_recovery=true` 调同一选片流程，读取完成后由 `handle_recovery_read_complete()` 调 `ECUtilL::decode` 重构 missing_on_shards；随后 READING→WRITING，将 returned_data 放入 `PushOp.data`，发送 `MOSDPGPush`。目标 `handle_recovery_push()` 调 ObjectStore transaction 的 write，事务提交并收到确认后更新 peer/global 恢复状态。整个 PG 尚有其他待恢复项时不能因一次解码／一次对象完成便标作 clean。

**保留按需恢复的例外。** 有些读请求遇到不可读对象会进入 `PrimaryLogPG::wait_for_unreadable_object()`，调用 `maybe_kick_recovery()`：对象需要恢复且尚未进行时，以高优先级调用 recover_missing 或 replica pushes 启动恢复；若已在 recovering 中则不重新启动或提升已有任务优先级，请求等待该流程。因此既不能说“每次降级读都会自动写回”，也不能说“读请求永远不会触发修复”。正确表述是：普通降级读只重构本次数据；某些读可发起独立持久恢复并等待；后台重建不依赖客户端读取。

**M1 的具体代入。** 此单目标示意先用于插件／后台恢复；当前18前台默认全k目标，不能直接承诺四helper小读（7.14）。若片段 D2 不可用、D0/D1/D3/L0 健康且请求需要 D2 对应范围，局部计划可选 `{0,1,3,10}`。前台得到 D2 字节就能满足本次允许服务的读；后台则要把该片完整需要的范围、对象版本和元数据写到恢复目标并确认。只丢局部或全局校验时也需要后台补齐，故自定义插件的恢复目标不能只支持原始数据。M1/M2 应分别记录降级读、实际 helper I/O 与持久重建验证，不能拿其中一个代替另外两个。

原 TSX 放在 Redis 中的有效尾部不属于 Ceph 通用 shard 状态本身；OSD 心跳／PG missing 不会自动知道某个 Redis 尾部键丢失。独立尾部存储若缺失，插件必须检测并报错／重新规划，其版本与可靠恢复仍需要专门契约，不能由 Ceph 自动恢复主片便推定尾部也已恢复。

### 7.18 FastTT-LRC 初版插件骨架（r16）

`[用户确定，2026-11-08]` 先确认现有直接纠删码工作流，再创建独立FastTT-LRC编码插件；参照当前18官方LRC的写法，详细内核允许留空，但注册、初始化、布局、选片、编码、恢复和测试要真实跑通。继续不用分布式虚拟集群；人读说明为docs/fasttt-lrc-design.md，保持简洁，本文保存完整接续事实。

**本轮落地与范围。** 新插件为 `tsx_lrc`，类 `ErasureCodeTsxLrc : public ceph::ErasureCode`，不是继承final的旧TSX或官方LRC。新Plugin类提供标准factory／init／version入口。复制的是官方Layer组织和本层编号映射思路，没有复制JSON通用解析器，也不动态包装另一个lrc对象；只需ISA子插件，无ec_lrc新依赖。基线仍为官方18.2.7@6b0e988，TSX已提交HEAD8ad62fe，本轮及r15精简均为其上的未提交改动；未推送。旧tsx/tsx2/tsx4算法不改，父四文件及根单补丁不改。

**模式必须显式。** `plugin=tsx_lrc mode=scaffold k=8 m=2 locality=4` 为当前可运行配置，k/m/locality可省略后使用这些默认值；不支持其他值、官方l参数、外部mapping/layers或自定义CRUSH分组。m只表示2个全局校验，接口返回数据8、总片12、全部校验4，默认identity物理编号。`mode=scaffold` 的全局层是ISA cauchy占位，两局部层是ISA reed_sol_van的m=1真实XOR；没有TT移位或Redis尾部。缺mode返回-EINVAL，`mode=fasttt`经真实全局层创建路径进入 `init_fasttt_global_layer()`，清空子对象并返回-EOPNOTSUPP(-95)。禁止给空内核返回0、把占位全局校验称为G+/G-或拿它测FastTT性能。

固定布局与三层如下；8、9只是未来TT全局的位置，当前存ISA校验，不是已发布TT存储格式：

```text
mapping: DDDDDDDD____
global:  DDDDDDDDcc__   data=[0..7], coding=[8,9]
local0:  DDDD______c_   data=[0..3], coding=[10]
local1:  ____DDDD___c   data=[4..7], coding=[11]
L0=XOR(D0..D3), L1=XOR(D4..D7)
```

`Layer`实际保存data、coding、chunks、erasure_code；chunks=data接coding。本轮用固定C++表构造，不解析上述字符串。调用子插件时按chunks顺序重排为本层0..k+m-1，回调后映回物理ID；bufferlist是引用，不为每一层拷贝整片payload。

**规划契约。** 输入want和available，输出RepairPlan.inputs及有序RepairStep(layer,helpers,targets)。先从available维护known，逆序尝试本层缺片数不超过本层校验数的恢复；每成功一步只增加已知片。全局恢复可能解锁局部校验，所以重复遍历，直到want全部已知或本轮无进展返回-EIO。每步增加known，最多补12片，不会无界自旋。随后从want反向追踪步骤依赖，移除无关步骤和输入。该启发式不保证任意故障下全局最少I/O。

例如D2目标只需{0,1,3,10}；即使另一组L1也丢失，不将其4个数据加入D2的读取。D0/D1同组双丢失采用全局层的{2,3,4,5,6,7,8,9}。D0与L0同时丢失时，先全局恢复D0，再局部重算L0。解码仅把step.helpers交给子插件；使用私有工作map，输入片保持字节不变，最终只向外发布want；未读取但被基类预分配的片不冒充有效输出。检查ID、空输入和等长条件；失败输出为空。

**当前容量与未支持组合。** 在12片所有1..3擦除共298种集合中，此逐层ISA骨架每长度能恢复266种，另外32种明确拒绝：同组3数据（8种），或同组2数据＋1全局（24种）。这是当前逐层规划边界，不证明这些码方程数学上不可解，更不代表真正TT方案不能恢复。1..2擦除共78种全部通过。不得将“298种用例执行完毕”写成“298种TT恢复成功”。未来TT联合策略必须单独完成第5节要求。

### 7.19 Layer与普通k+m编码的解释口径（r17）

`[用户要求＋当前18源码对照，2026-11-08，E-LAYER-r17]` 用户此前未接触Layer，要求举例解释其与“原数据切k片、再编码m校验”的区别，并写入人读设计。本轮只更新docs/fasttt-lrc-design.md和本文，不改编码／规划／构建脚本；r16测试记录保持原身份，不新增运行通过结论。

**核心口径。** Layer表示一次指定输入／输出的编码任务，不是另一份原文件或一套独立存储池。原始数据只切一次，层间复用同一条带的已有片与缓冲；校验也可成为下一层的输入。Layer.data是本层输入角色，不保证是原始数据；Layer.coding是本层输出角色，子插件的k/m由这两者大小决定，不直接沿用最外层profile的k/m。LRC外部仍能表示为k数据＋m_total校验，差异在生成方程、依赖范围和恢复选片，不是另有一套专用接口。

**统一小例子。** 原始16KiB切D0..D3四个4KiB片。普通RS4+2直接从四数据生成G0/G1，保存6片24KiB payload。官方LRC4/2/3先做同样全局编码，再执行局部D0,D1,G0→L0和D2,D3,G1→L1；三层子插件分别为4+2、3+1、3+1。物理排列[0:D0,1:D1,2:G0,3:L0,4:D2,5:D3,6:G1,7:L1]，mapping为DD__DD__，全局chunks=[0,1,4,5,2,6]，局部chunks分别[0,1,2,3]、[4,5,6,7]。最终8片32KiB payload，不能把层的输入重复相加成6+4+4。profile m=2为全局数，get_coding_chunk_count=4、get_chunk_count=8。

局部单校验用XOR作具体例子：L0=D0 XOR D1 XOR G0。D0缺失，读取D1/G0/L0三个helper，共12KiB，而普通RS4+2所列全局路径读取D1/D2/D3/G0四片，共16KiB。逐字节示例已生成D0=0x01、D1=0x02、G0=0x04，则L0=0x07，恢复0x07 XOR 0x02 XOR 0x04=0x01。D0/D1同组双丢失超过局部m=1，尝试全局G0/D2/D3/G1四输入。以上是方程与读取字节推算，不声称本轮执行官方LRC运行实验，也不把单目标helper数当作当前18完整前台请求的实际读取量。

**与同开销普通码的区别。** 普通RS4+4与上述LRC都保存8片，但RS四校验为全局MDS方程，LRC两全局＋两局部形成不同依赖；标准RS4+4能恢复任意四片擦除，不能仅凭LRC也有四校验就继承同样容错。局部修复收益须与额外冗余／容错结构一并解释。

**对应当前FastTT骨架。** 三层为8+2、4+1、4+1，局部组只含原始数据，分别D0..D3→L0、D4..D7→L1，不依赖G0/G1，逻辑上不必等待全局层；当前实现仍顺序执行。每层是同一个ISA插件的独立参数实例，非每层必须一种不同算法。此差异来自布局选择；官方低层layers也能表达数据分组。真正TT内核／尾部仍未实现，不因本次概念说明改变r16占位身份。

依据为当前18的ErasureCodeLrc::parse_kml/layers_init/encode_chunks/decode_chunks、ISA的m==1 XOR分支，以及tsx_lrc的固定Layer表。人读文档已将上述例子、每层k/m表、共享输入含义、单／双故障和同开销对比写清；本文保留足以接续的摘要，不能要求后续agent回读聊天。本轮验证UTF-8、代码围栏、源符号／表述与文档差异，不运行算法测试。

### 7.21 encode_chunks／decode_chunks的实际数据契约（r19）

`[用户要求＋当前18源码核验，2026-11-09，E-CHUNK-ABI-r19]` 本轮只补人读设计和本文。核对当前Ceph18的ErasureCode::encode_prepare/encode/_decode/decode/decode_concat，ECUtil的encode与两条decode路径，ECBackend选片及全k前台目标，以及原ErasureCodeTsx和新ErasureCodeTsxLrc的实际参数访问。以下是源码推得的契约，非新运行实验；旧r16测试记录不变。

**编号与单位。** 以下采用identity mapping、k=8、一次in长32768B、B=4096B。物理片号是map key，不是OSD号或第几个输入条目；片内t才是字节偏移。数据Di[t]=in[i*B+t]，0≤t<B。各数据起始字节依次0/4096/8192/12288/16384/20480/24576/28672，结束为下一起始点或32768；非整齐输入由get_chunk_size与encode_prepare补齐，不据此宣称旧TT支持任意长度。

| 片号 | 原tsx默认8+3 | 新tsx_lrc当前scaffold |
| --- | --- | --- |
| 0 | D0，in[0,4096) | 同左 |
| 1 | D1，in[4096,8192) | 同左 |
| 2 | D2，in[8192,12288) | 同左 |
| 3 | D3，in[12288,16384) | 同左 |
| 4 | D4，in[16384,20480) | 同左 |
| 5 | D5，in[20480,24576) | 同左 |
| 6 | D6，in[24576,28672) | 同左 |
| 7 | D7，in[28672,32768) | 同左 |
| 8 | G+主片 | ISA全局G0主片 |
| 9 | P0主片，无移位 | ISA全局G1主片，不能称TT的G− |
| 10 | G−主片 | L0=XOR(D0..D3) |
| 11 | 不存在 | L1=XOR(D4..D7) |

原tsx的局部指针数组chunks[i]是encoded[i]的字节地址；decode的data[i]来自decoded[i]、coding[j]来自decoded[k+j]，因此coding[1]对应物理9的P0。k/m来自实例初始化，不是两个_chunks函数的逐次参数。原G+/G−的B字节主片之外还各需224B有效尾部，当前由插件另行分配448B并SET/GET Redis，不包含在map中；并非每条decode分支都访问Redis。新scaffold尚无TT尾部，不能因其主片等长便认为TT存储问题已解决。

**编码的两层参数状态。** 公开encode(want,in,&out)的in是一次逻辑编码单元，out按接口约定初始为空。want是希望得到的输出片号集合，不承载payload，通常为全部n片，也可只要校验。当前新LRC在私有work上调用基类encode_prepare：0..7准备为已知数据，8..11按get_chunk_count−get_data_chunk_count分配B字节校验空间；不足数据部分补零。完整输入一般用substr_of引用并重建连续／对齐缓冲，不等于无条件深拷贝8份数据。校验create_aligned只分配，内容不保证为零。

低层encode_chunks(want,encoded*)的encoded已是输入输出工作map，不能按空输出map理解。读取其中数据并写入校验空间；want为子集也不意味着只准备该子集条目。当前骨架的每一层layer_want都包含该层全部编号，因此实际计算三层全部校验，最后encode仅发布want；旧基类直接在外层encoded上准备／计算／删去非want，新类采用私有work以便先检查错误。每次返回int为0或负errno，实际字节在bufferlist中；新类已修正旧Ceph18 base encode忽略encode_chunks错误的包装行为，原TSX仍受旧基类行为约束。

**解码的三个参数。** want_to_read是必须提供有效内容的目标ID，既能含数据也能含校验，亦可包含已经可读的片；不等于helper集合或所有未提供片。chunks是本次真正可用的输入map，只认可已有key及有效payload；缺key表示本次未提供，既可能实际丢失也可能只是没读。不能用全零buffer替代缺key，因为find/count会将它识别成已有输入。每片来自同一条带的相同片内范围，长度一致。

decoded*在进入低层时已是工作map：基类_decode对已有输入复制bufferlist引用并做对齐，对所有不在chunks里的ID新分配B字节恢复空间，然后才调虚函数decode_chunks。输入和工作map可共享底层buffer，map复制不等于payload私有副本；const chunks约束map访问，不能据此推断所有别名都不可写。后续内核应显式区分只读输入和可改scratch。原TSX确实用chunks.find判断缺失，却从decoded取data/coding指针，不能换成从chunks为缺片取地址。

**单D2恢复，精确工作状态。** 对新布局want={2}，minimum选择{0,1,3,10}，测试只提供chunks={0:D0,1:D1,3:D3,10:L0}。公开decode的out初始空；新包装建立私有work，ErasureCode::_decode把work准备为{0:D0,1:D1,2:未填B空间,3:D3,4:未填,5:未填,6:未填,7:未填,8:未填,9:未填,10:L0,11:未填}，再以&work作为低层decoded。所有条目存在且长B，不代表所有内容有效。D4..D7等可以健康但未读；不能据decoded.count或长度把它们加入输入。

计划执行后只新填2的D2，原0/1/3/10继续有效，其他未填空间在此例仍未计算。当前decode包装只发布out={2:D2}，失败则不发布输出。通用ErasureCodeInterface允许返回want之外的额外有效片，但不允许发布未完成片；这正是稀疏LRC不能直接把整个基类work当结果交回的原因。若want已全部在chunks中，_decode直接引用返回，根本不调用decode_chunks；局部计算不应依赖每次都会进入回调。

**子插件又是一套局部编号。** 全局层外ID[0..9]对应本层[0..9]；local0外ID[0,1,2,3,10]对应[0,1,2,3,4]；local1外ID[4,5,6,7,11]对应[0,1,2,3,4]。上例local0回调参数为layer_want={2}，layer_chunks={0:D0,1:D1,3:D3,4:L0}，layer_decoded={0:D0,1:D1,2:未填,3:D3,4:L0}。子插件写本层2后映回外层2；L0在子回调的key是4，绝不是10。当前Layer.erasure_code的encode_chunks/decode_chunks直接调用低层接口，层工作缓冲和编号重排必须由我们的调度代码准备。

**上层输入与输出边界。** ECUtil::encode先要求整理后的in按stripe_width对齐，逐stripe取buf调用ec_impl->encode，再把每条带同片号结果追加到out[i]；插件看到的不一定是整对象或原始客户端写入片段。例两条带64KiB逻辑输入，B=4KiB时最终上层out[0]是两条带D0的拼接、长8KiB，不是整文件开头连续8KiB。

恢复片路径ECUtil::decode(map输出)以out的key构造need，获取minimum并逐条带取各输入片，再调用ec_impl->decode(need,chunks,&out_bls,sinfo.get_chunk_size())；chunk_size为B而非原对象大小，当前基类和新包装未用此参数改变分配，而是按收到的chunk长度准备工作。ECBackend可能依据配置提供minimum的有效超集；契约不要求chunks恰好等于minimum，独立测试刻意严格只给minimum。

完整数据路径ECUtil::decode(bufferlist输出)逐条带调decode_concat；当前继承的ErasureCode::decode_concat构造全部k数据目标，直接调用_decode而不是虚函数decode，再按数据顺序拼接。这一路不经过新decode包装的结果裁剪，但内部只取已要求恢复的k个数据片形成连续输出。Ceph18前台默认目标为全部k数据；本节{2}仅作单片恢复／独立插件测试，不将四helper能力等同于完整前台请求的总读取数。

这些接口没有对象名、OSD号、磁盘地址参数，不在回调内做普通shard网络读取或持久写回。系统层取走的是主片bufferlist并负责后续存储／请求返回；移位尾部的额外身份与持久化仍是T1待解决契约。直接调用_chunks必须自行满足低层缓冲准备条件，不能把公开encode/decode初始空out的约定照搬到底层。

本轮只读上述当前18代码、重整人读设计并保存本文，校验索引表、源符号、围栏与源码哈希；未运行编译、算法、Redis或集群，不新增性能／正确性通过结论。

## 8. 两个里程碑共用的 Ceph 接入与尾部闭环

`[设计要求／待实现核验]` 仅增加 erasure-code profile 参数不足以完成新方法：

| 层次 | 必须明确的契约 |
| --- | --- |
| tsx 内核 | 输入和输出片段语义、布局／长度、所需尾部、错误返回、线程拥有权 |
| 插件层 | 新编号到 Ceph chunk index 的映射、所需片段选择、缓冲生命周期、全部任务完成后返回 |
| 读取路径 | 真正只读取计划所需片段；12 片布局不继承“任取 8 片”的假设 |
| 写入与持久化 | 数据、校验与尾部的对象／条带／版本身份一致；失败或重启后不混用旧尾部 |
| 修复与重建 | 既恢复数据也补齐丢失校验和尾部；重建成功后再次读回核对 |
| 故障域 | 核对一台机器或一个 OSD 会丢几片，不把片段数量直接当物理节点容错 |

最低系统验证顺序：隔离测试池完整对象写 → 读回比对 → 指定 OSD 不可用后的降级读 → 替换／恢复 OSD 重建 → 再次比对 → 重启相关服务／测试集群后比对。为每一步记录数据、4 校验、尾部和版本一致性证据。

本节描述的是待验收要求。当前 TSX 主实现的尾部存取局限见第 7 节；不能由“用了 Redis”推导出已满足持久化、原子性或故障重建。

必要尾部缺失、长度不符或版本不符时，应报错或重新规划，将对应输入标为不可用；**未知尾部不能当作已知零填充**。数学定义中片段范围外的零与丢失的真实校验尾部是两回事。

新旧布局必须有显式配置／格式身份和兼容性边界：原 `8+3`、现有 `tsx4` 的四全局校验、新 M1 的两全局＋两局部不是同一种码。设置 `m=4` 不会自动实现 M1。先用独立测试池验证新布局，防止旧对象被错误的编号／解码器解释；这不等同于已实现在线格式迁移。

## 11. 后置方向：保留理解，避免混入当前完成度

### 11.1 增量更新

`[后置设计]` 已有对象覆盖写时，利用编码线性性：

```text
delta = old_data XOR new_data
new_parity = old_parity XOR 编码(delta)
```

FastTT 的 delta 更新位置随列偏移移动；ISA-L RS 也支持增量更新，公平比较应包括双方增量和局部重算。候选工作为区间映射、合并同一校验块读改写、SIMD 与差分／重算／整编码选择，且计入读旧数据／旧校验、等待批次和真实 I/O 成本。

例：原 8＋3 布局中 D1 的 `[4096,8192)` 改写 4KiB，G+ 更新 `[4128,8224)`，P0 更新 `[4096,8192)`，G- 更新 `[4288,8384)`；按 4KiB 块计可能是 2／1／2 块，RS 同位更新各 1 块。这只是地址范围分析，不是实际 I/O 测量。新 12 片布局的更新还涉及局部校验，不能原样套用原 8＋3 结论。

若恢复此方向，须先重新确定范围，并设计数据、校验、尾部同版本提交及失败恢复语义。

### 11.2 更一般的局部修复码与码转换

这里保留另一类构造的最小理解，避免与 M1 混淆：先把原始序列分成若干分支，各自做全局 Two-tone 编码，再做局部 Two-tone 编码，并通过循环错位放置把相关序列分散到节点。一个节点可能存多条序列，因此“访问节点数”与“读取序列／片段数”不是同一计数。

一种局部性定义为：修复组大小 `r+delta-1`，同组最多 `delta-1` 个节点失效时，可由同组任意 `r` 个存活节点修复。例如 `r=2,delta=3` 对应 4 节点一组、最多坏 2 个时由另 2 个节点修复。这不是第 5 节的一片段语义布局，不能直接移用参数或容错结论。

`repair locality` 关注固定配置下修复失效节点要访问多少 helper。`conversion` 的目标是把 `lambda` 条初始码字合并成一条末态码字；在此类构造中，`n` 为码字节点数，原始序列数为 `M=r*k`，保持 `r` 时有 `k_final=lambda*k_initial`。这个等式本身不保证提高码率：保持局部参数与每节点存储量相同时，还需 `n_final<lambda*n_initial` 才能减少节点／序列层面的总存储，实际字节还须计入移位尾部。能否低成本转换另取决于生成矩阵兼容性，不能只拼接数据就宣告完成。

转换并非任意改局部性参数，也不是 M1 必须同时完成的功能。当前没有本项目的转换实现或对应性能验证，不将这些构造的访问复杂度换算为 FastTT 加速倍率。

### 11.3 跨地域预取与片段来源调度

THEIA 代表一种系统层思路：primary OSD 先收集所需片段、重构数据块，再向客户端发送；在发送当前块时，提前获取和重构后续块，用有界缓存控制预取数量，并依据链路负载调整所取片段的来源。预取命中能减少后续请求等待，但也可能增加缓存、网络或解码争用；编码矩阵不因此改变。

这类调度优化网络等待，不等同于 CPU 编解码线程模式，也不等同于通过局部校验降低修复输入。对当前项目的借鉴是分别计量 CPU、磁盘和网络等待，并检查端到端效果。若以后与 M1 结合，来源调度仍须选择方程可解的输入集合，不能只数片段。当前不要求实现预取或来源分配服务，其既往系统收益不作为 M1／M2 的收益证据。
